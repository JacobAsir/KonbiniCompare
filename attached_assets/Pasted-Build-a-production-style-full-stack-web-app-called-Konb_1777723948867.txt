Build a production-style full-stack web app called “KonbiniCompare”.

High-level goal:
KonbiniCompare is a Japan-first shopping decision assistant that helps users compare everyday consumer products in Japan and choose the option that best matches their needs.

Core product idea:
The user compares products from convenience stores, supermarkets, or drugstores.
The app ranks products based on user preferences and explains the trade-offs clearly.
This is not a generic chat app and not a random recommendation engine.
It is a structured consumer decision support product.

Primary user problem:
Japanese stores offer many similar consumer products, and comparison takes time.
Users want help choosing the best option for them based on budget, nutrition, ingredients, allergies, caffeine level, skin sensitivity, convenience, and value-for-money.

Target users:
- Japanese consumers
- students
- office workers
- foreign residents in Japan
- health-conscious shoppers
- beauty/skincare buyers
- supplement buyers

Important product principle:
The ranking must be understandable.
Users should always see why one product is ranked above another.
The app must show trade-offs and incomplete data clearly.

This version should be stateless by default.
Do NOT add authentication, a database, or user accounts unless explicitly requested later.
Use demo product fixtures and optional temporary session state only.

Tech stack:
Frontend:
- Next.js 14+ with TypeScript
- App Router
- Tailwind CSS
- clean comparison-first UI
- mobile-first responsive design

Backend:
- Python FastAPI
- product normalization service
- deterministic ranking engine
- category-specific scoring layer
- explanation service
- optional OCR/image extraction abstraction
- mock dataset service

AI / model usage:
- Use Groq LLM for natural-language preference parsing and bilingual explanation
- Use Gemini optionally for image/label extraction if user uploads product labels
- The ranking engine must be deterministic and must not rely on the LLM for final scoring
- Build provider abstraction so models can be swapped later
- App must support mock mode without API keys

Architecture requirement:
Build like a real product, not a monolithic demo.
Use a clear layered architecture.

Use a gateway pattern:
- frontend calls backend API
- backend normalizes products

- no database writes
- no persistent storage

Supported product categories for MVP:
- drinks
- snacks
- supplements
- skincare
- household daily items

Required product behavior:
The user:
1. chooses a category
2. selects or enters 2 to 5 products
3. sets preferences and weights
4. submits comparison

The app:
1. normalizes product data
2. validates available fields
3. computes weighted scores
4. ranks products
5. shows strengths and trade-offs
6. explains the best option in Japanese and English
7. clearly flags missing information if product data is incomplete

Core MVP features:

- CTA to compare products

Ranking engine requirements:
Build a deterministic ranking engine.
Do not use the LLM to decide the ranking.

The engine should:
- accept user preference weights
- score products on normalized fields
- support category-specific rules
- return a weighted total score
- output per-dimension scoring breakdown
- support missing-value penalties or uncertainty flags

Example scoring dimensions:
- price
- caffeine amount
- calories
- sugar
- protein
- additives/ingredient simplicity
- pack size/value
- irritation risk or fragrance presence for skincare
- allergen conflicts
- convenience / portability

Important build rules:
- If product facts are missing, do not hallucinate them
- If the user uploads an image later, use extraction only to structure data, not to invent facts
- Always show which fields were actually used
- Ranking must be reproducible and inspectable
- Explanation must be grounded in actual product fields
